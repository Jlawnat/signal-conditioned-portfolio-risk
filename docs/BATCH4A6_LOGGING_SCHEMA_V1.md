# Batch 4A.6 local event schema v1

The implementation is `scripts/run_mpb_lifecycle_v5u_logged_v1.py` plus `src/portfolio/decision_execution_log_v1.py`. It is a separate copy of the V5-U research executor. It has not been run on historical or Norgate data in this batch. A future authorized run writes only to ignored local `audit/batch4a6_v1/<run_id>/`; an existing nonempty run directory causes an error. `--no-log` disables the event journal for comparison, while retaining the versioned economic output path. No telemetry or upload is used.

## Actual runner order and spec interpretation

The existing runner settles payments and applies ex-date adjustments before the T+1 opening mark. It then sorts pending sells before buys, fills whole orders or rejects an opening buy for cash or position-cap reasons, marks the post-fill open, and marks the close. At T close it calculates the current budget, plans MPB exits, applies the B/C overlay to those exits, then plans buys. Thus S1 is **after MPB exits and overlay, before buys**. It is not an overlay-only state. S2 is after all accepted buys and sells. The original runner has no partial-fill path, and deliberately blocks held or pending splits and composite actions. The final study session has no next-open decision in the original runner, so no S0–S2 is fabricated for that terminal session and no pair is scored.

## Files and logical chronology

Each JSONL row has `schema`, `run_id`, `policy_id`, `decision_id`, optional `order_id`, `decision_date`, `execution_date`, monotone `event_sequence`, `simulation_phase`, `simulation_timezone` (`America/New_York`), `information_cutoff`, `record_origin`, `strategy_config_hash`, and `data_manifest_hash`. Dates and phases are logical simulation markers, not broker submission timestamps. SHA-256 based IDs are stable for the same version, policy, dates, inputs, symbol and side. The configuration hash covers frozen reference configuration and the V5-U logged version. The data manifest hash combines the market action manifest, candidate CSV and dividend register hashes; it does not expose their raw contents.

| File | Records |
|---|---|
| `snapshots.jsonl` | S0 T-close predecision; S1 MPB plus overlay sells; S2 complete final plan; S3 next-open after payments/actions before fills; S4 after fills; S5 next close. A missing S3/S4 is recorded on a caught opening input failure. |
| `orders.jsonl` | Each candidate order's `PROPOSED`, `ACCEPTED`, `QUEUED`, `REJECTED`, `FILLED`, or `CANCELLED` events. `PARTIAL_PLAN_REJECTION` records shares excluded by planning limits. |
| `pairs.jsonl` | S4 minus S2 risk, positive part, and planned-compliant-to-opening-exceedance indicator for each adjacent pair. Includes `had_orders`, `had_overlay_intervention`, and A reference-only labeling. |
| `reconciliation.json` | Independent cross-file order ID, accepted quantity, fill quantity, terminal state and S2 membership checks. |
| `p3_lifecycle_v5u_<policy>_{daily.csv,trades.csv,summary.json}` | Versioned copies of the original economic result formats; never written to historical V5-U paths. |

S0–S5 snapshots contain `nav`, actual `cash`, `dividend_receivable`, `holdings_count`, position rows with shares, security ID when supplied, adjusted stop and mark, valuation price source/time, risk numerator/denominator, exposure, own and 4% reference budgets, excess, status and missing reasons. For S2, `cash` is actual T-close cash, `planner_projected_cash` is the original buy planner's separate estimate, `projected_execution_cost` is separate, and the risk denominator is **actual T-close NAV**. This is the spec's proposed convention and still needs research protocol approval before empirical claims. S4 uses actual post-cost NAV. Risk is `sum(shares * (max(0, price - adjusted_stop) + 0.01 * price)) / NAV` at both stages. Invalid NAV, marks, stops, cash, receivables or budgets result in `MISSING` and null risk, never zero.

Sell proposals record MPB quantity, additional overlay quantity and final netted quantity. Buy proposals record requested quantity before the cash cap, the risk, position, sector, volume and cash share limits, decision mark, stop, factor and cash available. `ACCEPTED` records the final planned quantity and estimated cost. Opening fill/rejection events keep the same order ID and record actual quantity, execution price, realized cost or reason. A candidate skipped before a positive order quantity is formed is not described as a proposed order. All orders that have reached `PROPOSED` must reach a terminal state; a caught simulation abort cancels open orders. The same-opening sell proceeds rule and all strategy thresholds are unchanged.

`pairs.jsonl` uses the **T decision budget** for the opening indicator, including Policy C. A's 4% comparison is labeled `policy_a_reference_only`; its own overlay requirement is false. `epsilon = 1e-9` exposure fraction is fixed in code for the synthetic suite. The pair file retains every valid adjacent session, including no-order sessions; the predefined `had_orders` and `had_overlay_intervention` flags support the three prespecified populations. Missing future data produce a missing pair, not a zero gap. Closing S5 uses its own newly computed closing budget and is separate from the opening indicator.

The runner provides stable ticker keys but no verified historical stable security ID in the V5-U input lineage. `security_id` is null unless a supplied candidate contains one. Full PIT traceability requires the unresolved licensed stable-ID join. The source executor does not support partial fills; the `PARTIALLY_FILLED` state is reserved for a future version and is never emitted by v1. It rejects splits, including synthetic split input, without changing that rule. Synthetic split arithmetic in the pure snapshot function tests adjusted-share representation, not executor split support.
